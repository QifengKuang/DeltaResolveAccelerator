# 本机与远程排查流程

先记录正在运行的版本、安装目录、游戏启动平台、故障时间和界面错误。不要在对局中重启加速器、调整网卡或移动目录。

## 克隆后首次运行

1. 克隆源码，执行 `build/Compile-App.ps1` 和 `tests/Test-Offline.ps1`。此时只验证界面和本地逻辑。
2. 按 [依赖说明](DEPENDENCIES.md) 准备官方 SDK、PowerShell 运行时，并在新电脑本机导入独立设备密钥。
3. 在设置中填写本机实际存在的 Steam、WeGame 路径。最多保存两个；运行哪个进程，就匹配哪个完整路径。
4. 在游戏不处于对局时开启加速，核对界面版本与连接状态，再测试一次实际入局。记录游戏内延迟及入口结果，区分“线路已连接”和“游戏确实发送了命中规则的解析请求”。

旧电脑的 DPAPI 密钥文件不能作为新电脑的配置迁移方案，也不要将本机运行记录提交到 GitHub。

## 连接动画持续或阶段没有变化

记录界面显示的当前阶段、本次已耗时和错误文字。连接动画表示启动任务正在处理，阶段来自后台状态；动画仍在动不代表阶段已推进。成功状态需要后台实际确认就绪。

上次成功耗时只是一条历史参考。超过该时长不能单独证明本次失败，也不表示还需等待固定秒数；没有历史记录时，不应凭空推定预计完成时间。若出现明确错误，按该错误定位问题，避免只依据动画或历史耗时反复重连。

## 重启后提示仍在运行或需要恢复

开着加速器正常重启或强制重启后，Windows、DHCP 及其他网络软件会重新建立网络状态。网卡编号、临时地址、接口优先级，甚至网卡集合都可能变化。跨重启仍要求整台电脑与旧快照一致，会把已经结束的连接一直显示为“网络配置仍有差异”。

客户端首次打开会自动执行一次恢复检查，重新开启连接前也会执行同一检查。正在运行的 worker 不会被自动恢复停止；后台状态轮询仍然只读。上次恢复已经完成时直接沿用完成结果，不会反复拿旧快照比较。

恢复先核对 Windows 开机时间、旧 worker 和所有归属进程的创建时间。确认属于上次开机后，不再用旧 PID 清理进程或扩展进程树，避免误操作重启后复用相同编号的新进程。随后完整读取当前网络，确认没有本应用 SDK 进程、服务、专属虚拟网卡、路由及 DNS 等残留，才结束旧会话。普通网卡、DHCP/APIPA、IPv6、WSL 或其他 VPN 的变化保留为诊断，不要求写回重启前状态。共享 Wintun 驱动本身不算本应用残留。

下一次开启由新 worker 在启动 SDK 前重新采集并保存完整基线。跨重启恢复不会启动线路或修改物理网卡、全局 DNS、代理和其他 VPN。未发生重启的会话继续按进程归属执行清理，并采用同一套当前资源释放判定。

库存确认释放后，仅删除旧会话精确目录中的临时线路凭据，保留日志、归属记录和旧基线；遇到路径重定向或不一致身份时停止处理。诊断报告保存失败不会推翻已核实的释放结果，界面会提示部分记录未能保存；完成状态本身仍须可靠写入。

旧基线可读取时，完整原始比较保留在本机 `backend/results/ui_recovery_comparison_*.json`；旧基线缺失或损坏时记录原因，不伪造或覆盖它，也不阻塞已经核实的跨重启会话释放。跨重启判定另记入 `ui_recovery_reboot_*.json`，记录当前快照和 `PreviousBootSessionReleased` 或 `PreviousBootSessionPending`。状态与归属记录采用临时文件刷盘后原子替换；基线在启动 SDK 前刷盘，降低突然断电导致的记录损坏风险。开机归属不一致、当前读取不完整或实际残留仍会保留证据并提示处理；本次恢复会对短暂库存读取失败最多重试三次。

“关闭并恢复”仍可手动重试。不要仅凭旧 PID 杀进程或直接清空恢复记录，也不需要全局重置 DNS/路由。已有轻量更新通道只分发 UI，本修复还包含后端脚本；只更新 EXE 不会获得新的恢复判定，需同步部署本提交的后端。新版 UI 对旧后端保留兼容。

## 移动安装目录或更换启动入口

先在原安装目录正常停止加速并退出客户端，再处理目录迁移或快捷方式。核对快捷方式目标、工作目录及实际运行的 `Accelerator.exe` 路径，避免打开旧副本。

运行记录可能保留旧的绝对路径。不要把整个 `backend/private` 或 `backend/results` 从旧目录直接覆盖到新克隆目录；其中不仅有恢复信息，还可能包含设备密钥。需要保留密钥时，使用应用既有导入方式，并保持同一获授权用户和设备的边界。

“目录移动后出现旧状态或退出异常”仍需针对实际目录变化验证。该仓库没有包含针对特定电脑的自动清理脚本。

## 有线与 Wi-Fi 切换

在停止加速后切换网络，再重新开启，便于建立当前网络基线。有线反复断开只能提示链路、接口或网卡侧问题，不能仅凭应用日志断言网线损坏；应结合 Windows 网络事件、网卡状态和网关丢包分开判断。

入口解析失败、应用恢复状态错误和对局延迟是不同观测结果，应分别记录时间与证据。界面报错文本现使用 UTF-8 输出，仍应保留完整错误文字以便定位。

## 未重启，关闭后仍提示网络配置差异

1.1.1 取消“整台电脑必须回到连接前快照”的停止条件。实际故障中，本次 SDK 停止成功、TUN 退出、残留进程为零，但 Tailscale 从 APIPA 切换到正常地址、WSL 新增虚拟网卡、无线网卡重新出现，仍触发旧错误。逐个增加 DHCP、RA 或 VPN 名称白名单无法覆盖动态网络。

现在普通关闭与同次开机恢复都先清理确属本会话的进程，再采集当前库存、检查本应用资源。当前完整清单无残留且清理成功即可结束；Tailscale、WSL、网卡切换、IPv6、其他 DNS/代理/路由变化完整保留为诊断，不重置、不回滚其他软件。检查只说明本次资源已释放，不说明外部网络配置正确或线路仍然连通。新连接仍执行既有线路和 UDP 验证。

短暂读取失败或 TUN 尚在消失时，按 250/500 毫秒退避重读，最多三次。读取不完整、SDK 仍在运行、专属网卡/路由/DNS/代理残留、无法确认归属的清理失败仍阻止新连接。进程身份损坏不会按旧 PID 强杀；旧网络快照缺失只影响诊断，不再永久锁住已释放的连接。

正常关闭的 `ui_connection_*.json` 记录 `ResourceRelease`、`NetworkResourcesReleased` 和重读次数；同次开机恢复另存 `ui_recovery_resources_*.json`。`NetworkEqual` 和 `NetworkConfigurationEqual` 仅记录全机快照是否一致，不参与资源释放判定。旧 RA/DHCP 分类函数保留用于历史诊断回归。

设计参考 [Tailscale Windows 路由协调](https://github.com/tailscale/tailscale/blob/main/wgengine/router/osrouter/router_windows.go) 和 [WireGuard 接口监视](https://github.com/WireGuard/wireguard-windows/blob/master/tunnel/interfacewatcher.go) 的自身资源管理方式。这里未替换 MNA SDK、未实现自己的驱动，也没有承诺切换运营商时游戏连接不断线。

完整自有文件包见[构建说明](BUILD.md)。旧 1.1.0 UI-only 更新通道不能分发后端修复，不应将完整包直接塞进旧更新器。

## 分享可复核的信息

可提供源码提交号、程序版本、发生时间、启动平台、连接阶段与已耗时、脱敏错误及离线测试通过/失败数量。原始密钥、SDK 认证响应、设备标识、局域网地址、用户目录和游戏日志中的令牌应留在本机；需要日志时先进行定向脱敏。
